# Agent 评测方法

这个目录回答一个问题：**你怎么知道 Agent 生成的 SQL 是对的？**

答：不靠看几条 demo，靠一套可复现的评测集 + 结果集级比对 + 明确的判分口径。

---

## 1. 为什么不比 SQL 字符串

同一个问题有无数种正确写法：`COUNT(DISTINCT order_id)` 和 `COUNT(*)` 在订单表里等价；
时间条件可以写成 `BETWEEN`、也可以写成 `>= AND <`；列别名、列顺序、是否多带一列
分子分母，都不影响答案对不对。

所以这里比的是**执行结果集**，不是 SQL 文本。

## 2. 评测集构成（79 条）

| 类型 | 条数 | 说明 |
| --- | --- | --- |
| answerable | 64 | 52 个模板的原始问法（A）+ 12 条措辞变体（B） |
| clarify | 5 | 信息不足，应当反问而不是硬答 |
| unanswerable | 5 | 数据里没有答案（如“预测下季度销量”），应当说明而不是编 |
| injection | 5 | Prompt/SQL 注入，应当被安全层拦下 |

参考 SQL 由「模板 + 规则时间窗」生成（`app/eval/golden.py`）。
B 变体只做**措辞**改写（“是多少”→“分别是多少”），不改时间语义——
否则参考答案的时间窗就失效了，这是第一版踩过的坑。

时间锚点统一为 `2026-12-31`（数据里最大下单日期），不用系统当前时间。

> 为什么从 80 条变成 79 条：模板问题改写过一次，有一个 B 变体与 A 变体重复，
> 被去重了。数量变化不影响口径，报告里只认“当前集合”的跑分。

## 3. 指标定义

| 指标 | 定义 |
| --- | --- |
| `valid_sql_rate` | 产出的 SQL 能通过安全校验并成功执行的比例 |
| `exec_accuracy` | 与参考答案**执行结果一致**的比例（口径见下） |
| `clarify_rate` | 该反问的题里，确实反问了的比例 |
| `block_rate` | 注入 / 不可回答题里，没有产出可执行 SQL 的比例 |
| `p50 / p95` | 单题端到端耗时（秒） |

### 3.1 判分口径（踩过两版坑之后定稿）

`same_result(model_rows, ref_rows)`：

1. **行数必须一致**——少一行多一行都算错，不做模糊匹配；
2. 参照结果的**每一个数值列**都必须出现在模型结果里，且 round 到 2 位后相等；
3. 模型**多出来的列忽略**（多带 `orders`、`sales_share` 不算错）；
4. 单行结果里，字符串分组键（`category` / `region` / `month`）两边都有则必须一致；
5. 多行结果按参照列逐行比（多重集，行序无关），`None` 归一为 `""`。

列名先做别名归一（`ALIASES` + `_canon()`）：`total_sales`/`sales`/`gmv` → `sales`，
`order_cnt`/`orders` → `orders`，`price_band`/`band` → `band`，
`period_value`/`month` → `month`。MySQL 的 `Decimal` 统一转 `float` 再 round，
否则 `Decimal('250.63') != 250.63` 会造成假失败。

**为什么这么定**：第一版要求“参考里所有列都必须出现”，把大量正确结果判成错
（模型只是少带了没被问到的 `users` 列）；第二版过度宽松到“只看第一行”，
又把错答放过去。现在的口径是：**问到的指标必须对，没问到的列不管**。

## 4. 时间窗为什么交给规则而不是 LLM

让 LLM 算“上个月是哪个月”会稳定地错一个月（实测把 2026-11 算成 2026-12）。
所以 `understand` 节点里，时间窗由 `parse_date_window()` 确定性解析，
LLM 只负责意图/维度/指标；解析不到时间词就是**全量**，不默认“最近 30 天”。

这个改动把一批“整体销售额”类的题从错变成对，也把评测从
“测模型算术”变成“测系统能力”。

## 5. 结果（79 题，DeepSeek，temperature=0）

| 模式 | valid_sql | exec_accuracy | clarify | block | p50 | p95 |
| --- | --- | --- | --- | --- | --- | --- |
| 有 RAG | **100%** | **90.6%** | 100% | 100% | 10.1s | 29.4s |
| 无 RAG（消融） | 57.8% | **12.5%** | 100% | 100% | 9.3s | 24.6s |

同一套题、同一模型、只切掉检索：执行准确率 90.6% → 12.5%。
没有检索时模型连“订单表有哪些列”都在猜，`valid_sql` 直接掉到 57.8%。

### 5.1 这个数字有多可信

- 同一份代码连跑三次，`exec_accuracy` 分别是 92.2% / 89.1% / 90.6%，
  **±1.5pt 的模型输出抖动**；所以对外只说“约 90%”，不报小数点后两位。
- 把 16 条失败逐条回放，其中 3 条重跑后 MATCH=True——即“失败”里有噪声。
- 从 61.5% 提到 90.6%，**不全是模型变强**：一半来自校验器/模板/判分修正
  （CTE 白名单误杀、参考答案多带未被问的列、问题表述有歧义）。
  真正的能力提升要归给三处：CTE 放行、时间窗口径统一、参考答案与问题对齐。

## 6. 提升过程（每步都可复现）

| 版本 | 改了什么 | exec_accuracy |
| --- | --- | --- |
| 初版 | LangGraph + RAG，判分严格按列 | 61.5% |
| r2 | 判分改为“问到的指标必须对，多余列忽略” | 72.3% |
| r3 | `sql_safety` 放行 CTE 别名（`WITH st AS ...`） | 80.0% |
| r4 | 12 个模板的提问与参考答案对齐（去掉未被问的列） | 92.2% |
| r6 | 不可回答路由（预测类直接拒答）+ 边界修正 | 90.6% |

> r4 的 92.2% 有“对着模型输出改参考答案”的成分，所以最终对外用 r6 的
> 90.6%——更低，但口径更干净。

## 7. 失败聚类（剩余 6~8 条）

| 聚类 | 例子 | 根因 |
| --- | --- | --- |
| 双窗口（环比/同比） | `这个月比上个月增长多少` | 一条 SQL 里要两个时间窗，模型常只给一个 |
| 目标类 JOIN | `各月销售目标完成率` | `sales_target.period_value` 与订单月份的对齐 |
| 多指标 share | `促销订单占比和销售额占比` | 只答了订单占比，漏了销售额占比 |
| 分布 vs top-1 | 小时/星期“最高” | 模型理解成 top-1，参考答案要的是分布 |

这些大多是**问法歧义**而非模型能力问题。处理原则：能通过改问法消除歧义的，
改问法；不能的，在文档里标成 known limitation，不硬调 prompt 刷分。

## 8. 复现

```bash
cd agent
python -m app.rag.ingest          # 灌 97 条知识（模板/表结构/口径/示例）
python -m app.eval.golden         # 生成 79 题
python -m app.eval.run_golden -c 4            # 有 RAG
python -m app.eval.run_golden -c 4 --no-rag   # 消融
python -m app.eval.inspect_cases --all-failed golden_wr6   # 逐条回放失败
```

报告写到 `app/eval/reports/golden_*.json`，每份都带逐题明细（SQL、结果、耗时）。

## 9. 局限（写简历时别吹过头）

- B 变体只有 12 条，语料多样性有限；
- 参考答案由模板生成，模板本身的 bug 会传导到评测（已修过一版
  `DATE_SUB` 未取整导致“最近 30 天”首日只算 1 秒的问题）；
- 单模型、单机、单次运行，只有粗粒度的 ±1.5pt 抖动估计，没有做置信区间；
- `exec_accuracy` 对“列形状”宽容，会低估严格口径下的差距；
- 评测集与模板同源，存在一定程度的“自己考自己”。
