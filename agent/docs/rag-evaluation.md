# RAG 检索评测：从「哈希词袋」到「BGE-M3 + 混合检索 + 精排」

> 这份文档记录 Agent 知识库检索的改造过程与可复现的评测数字。
> 所有结果都可以用文末命令在本地重跑，不依赖人工标注平台。

## 1. 为什么要做这件事

改造前的 `vector_store.py` 把 SQL 模板存进 Milvus，但向量是用 **md5 字符 bigram 哈希** 得到的 256 维「词袋向量」：

```python
h = int(hashlib.md5(gram.encode()).hexdigest(), 16)
vec[h % 256] += 1
```

它没有任何语义能力：用户问「上个月手机品类卖得怎么样」，模板写「手机品类月度销售额」，
字面重合度低，余弦相似度只有 0.167，直接掉出召回。所谓「Milvus 语义检索」名不副实。

这次改造做三件事：

1. **真 embedding**：SiliconFlow `BAAI/bge-m3`，1024 维，带磁盘缓存；
2. **混合召回**：dense（Milvus HNSW）+ sparse（客户端 BM25）→ RRF 融合；
3. **精排**：`BAAI/bge-reranker-v2-m3` 对融合候选重排，再 MMR + 类型配额组装上下文。

## 2. 评测集怎么来的

| 项目 | 规模 | 说明 |
|---|---|---|
| 知识库 | 97 条 | 52 个 SQL 模板 + 4 张表结构卡 + 26 个业务词 + 15 条示例 |
| 评测题 | 81 题 | easy 30 / medium 34 / hard 17 |
| 标注 | 单相关文档 | 每题标 1 个 gold 模板（`tpl_*`），按名次算 Recall@K / MRR / nDCG@5 |

题目不是从模板标题原样抄的，而是按真实用户问法改写：

- easy：与模板问法接近（「上个月销售额和订单量是多少」）
- medium：换说法/带业务黑话（「钱主要被哪些品类赚走了」）
- hard：省略主语、口语、需要澄清或跨口径（「这个月比上个月是涨了还是跌了」）

指标定义见 `app/eval/metrics.py`；单相关文档时 `IDCG=1`，`nDCG@5 = 1/log2(rank+1)`。

## 3. 结果（81 题，top_k=20）

| 策略 | R@1 | R@3 | R@5 | R@10 | MRR | nDCG@5 | p50 | p95 |
|---|---|---|---|---|---|---|---|---|
| hash-256（旧方案） | 0.679 | 0.778 | 0.778 | 0.877 | 0.742 | 0.738 | <1ms | <1ms |
| dense（BGE-M3） | 0.889 | 0.963 | 0.963 | 0.975 | 0.924 | 0.932 | 14ms | 18ms |
| bm25（jieba/bigram） | 0.790 | 0.901 | 0.926 | 0.926 | 0.845 | 0.864 | 16ms | 36ms |
| hybrid（RRF） | 0.889 | 0.938 | 0.963 | 0.963 | 0.919 | 0.929 | 14ms | 22ms |
| hybrid + rerank | **0.876** | **0.975** | **0.988** | **0.988** | **0.929** | **0.944** | 376ms | 466ms |
| + MMR + 配额（生产上下文） | 0.889 | 0.938 | 0.938 | 0.975 | 0.914 | 0.915 | 411ms | 693ms |

分难度 Recall@5 / MRR：

| 策略 | easy | medium | hard |
|---|---|---|---|
| dense | 0.967 / 0.935 | 1.000 / 0.971 | 0.882 / 0.810 |
| bm25 | 0.933 / 0.855 | 0.971 / 0.887 | 0.824 / 0.740 |
| hybrid | 0.967 / 0.944 | 1.000 / 0.949 | 0.882 / 0.814 |
| hybrid + rerank | **1.000 / 0.925** | 1.000 / 0.971 | **0.941 / 0.853** |

**一句话结论**：R@5 从 0.778（哈希词袋）提升到 **0.988**（BGE-M3 + rerank），
hard 子集 R@5 从 0.765 提升到 **0.941**，端到端检索 p50 约 376ms（rerank 占大头）。

## 4. 几个反直觉的点（面试会问）

### 4.1 hybrid 为什么没有明显赢过 dense？

语料只有 97 条，且 BGE-M3 对中文短问句已经很强，dense 本身接近天花板。
BM25 的价值在 hard 子集的 MRR（0.810 → 0.814，几乎持平）和**精确串**场景
（订单号、SKU），不是整体 Recall。这个结论是**测出来的**，不是拍脑袋：
如果继续加词表、调权重去「凑」一个更好看的数字，就是过拟合评测集。

### 4.2 rerank 有效，但 MMR 会拉低模板召回

- rerank 把 R@5 从 0.963 拉到 0.988，hard 从 0.882 拉到 0.941 —— 精排确实在纠错；
- 但生产链路里 rerank 之后还要过 MMR + 类型配额（3 模板 + 2 表结构 + 2 词表 + 1 示例），
  MMR 为了**上下文不重复**会把「语义相近的兄弟模板」往后排，模板召回自然下降。

这是**刻意的取舍**：检索指标衡量「找没找到」，上下文组装衡量「给模型的材料够不够全」。
所以生产默认 `stage="context"`，而评测表里的 `hybrid + rerank` 才是检索能力本身。

### 4.3 为什么不用 Milvus 原生 BM25？

服务端是 v2.4.0，稀疏向量 / BM25 Function 是 2.5 才有的能力。
语料只有百条量级，客户端 `jieba + BM25Okapi` 完全够用，还省一次网络往返。
如果语料涨到十万级，再迁到 Milvus 2.5 的 sparse + hybrid search。

## 5. 复现

```bash
cd agent
python -m app.rag.ingest                       # 灌库（97 条，embedding 有磁盘缓存）
python -m app.eval.run_retrieval               # 五组消融，输出 Markdown 表 + JSON 报告
python -m app.eval.run_retrieval --show-misses # 打印未命中/排名靠后的 query
python -m app.eval.run_hash_baseline           # 旧哈希方案基线
python -m pytest tests -q                      # BM25/RRF/MMR/指标单测
```

报告落在 `app/eval/reports/retrieval_*.json`，包含每题的 rank 与 top3，便于复盘。

## 6. 局限（写简历时不要吹过）

- 81 题、单相关文档标注，规模不足以支撑「显著优于」的统计结论，只能说明趋势；
- 题目由模板反写，存在一定「同源」偏差，真实用户问法会更脏；
- 目前只评检索，**没有评端到端 SQL 执行准确率**（W2 的 golden set 会补上）；
- rerank 走 API，376ms 的 p50 在生产上需要用本地模型或缓存优化。

下一步（W2）：把检索接进 LangGraph 节点，用 150 题 golden set 评
`valid_sql_rate` 与 `exec_accuracy`，并对比「有 RAG / 无 RAG」的差异。
