## 1. 一分钟项目自述（口播稿）

## 2. 一条问数的完整链路（先建立全局图）

```
浏览器
  │  POST /chat  （session_id + question）
  ▼
FastAPI  ── SSE 流式返回（thinking / sql / answer / chart / done）
  │
  ▼
LangGraph 状态机                              agent/app/graph/build.py:69
  understand   规则引擎先定时间窗 + LLM 抽意图
     │
     ├─ 有歧义 → clarify_answer（反问，不瞎猜）
     ├─ 答不了（预测未来/要建议）→ give_up_answer
     ▼
  retrieve     dense + BM25 → RRF → rerank → MMR → 按类型配额
     │
     ▼
  generate     输出 JSON：sql / confidence / assumptions
     │
     ▼
  critic       执行前自检（时间窗、指标、JOIN、空结果）
     │  └─ 不过 → 回 generate 重写（最多 2 次）
     ▼
  execute      sqlglot 白名单 → 只读连接 → 超时 → 行数上限
     │
     ▼
  analyze      结论 + ECharts 配置（最多 2 张图）
     │
     ▼
  finalize     写会话记忆、SQL 审计日志
```

**关键点（一定要讲出来）**：**时间窗不是 LLM 算的，是规则引擎算的**。LLM 只负责"理解问题要什么"，日期这种确定性的事交给代码。这一条决定了后面 90% 的准确率。

## 3. NL2SQL 安全：模型写的 SQL 为什么不能直接跑

### 3.1 他会怎么问

- "大模型生成的 SQL 你敢直接执行吗？"
- "怎么防注入 / 防它删库？"
- "为什么不用正则过滤关键词？"

### 3.2 一句话答法

> 不信任模型输出。SQL 先用 sqlglot 解析成 AST，在语法树上做白名单：只允许 SELECT、只允许查 3 张表、函数限定在白名单里、强制补 LIMIT；过了白名单才进只读连接执行。正则过滤挡不住注释、大小写、函数嵌套这些绕过方式。

### 3.3 展开

```python
# agent/app/sql_safety.py:55
def validate_sql(sql: str) -> str:
    statements = sqlglot.parse(sql, read="mysql")
    if len(statements) != 1:                 # 多条语句直接拒
        raise SqlSafetyError("只允许单条语句")
    ast = statements[0]
    if not isinstance(ast, exp.Select):      # 只允许 SELECT（含 WITH）
        raise SqlSafetyError("只允许查询")
    ...
    if ast.args.get("limit") is None:        # 没写 LIMIT 就补一个
        ast = ast.limit(settings.max_rows)
    return ast.sql(dialect="mysql")
```

三个当时踩出来的细节：

1. **`WITH ... AS (...)` 被误杀**：CTE 别名被当成"白名单外的表"。修法是先把 `exp.CTE` 的名字收集起来，做表校验时跳过；同时建一张"别名 → 真实表"的映射，CTE 里套的子查询也要能追到真实表。
2. **`YEARWEEK(order_time,3)` 被误杀**：sqlglot 把它解析成 `exp.Anonymous`，`sql_name()` 返回 `"ANONYMOUS"`，白名单当然不认。修法是取 `func.this` 的真实函数名。
3. **`IF(..., ...)` 这种也走 Anonymous**，所以白名单要按"真实函数名"匹配，不能按节点类型。

**执行层还有三道锁**（不只是 AST）：

- 连接是**只读账号**，物理上写不了；
- 单条 SQL 有**超时**（`MAX_EXECUTION_TIME`）；
- 结果集有**行数上限**，导出走流式，避免大结果集把内存打爆。

### 3.4 追问预判

| 追问 | 答法 |
|---|---|
| "正则黑名单不行吗？" | 不行。`SELECT` 里可以藏子查询、注释、大小写混写、`/*!50000 DROP*/`；AST 是在语法结构上判断，绕过成本高得多 |
| "模型写 `DELETE` 怎么办？" | 解析出来不是 `Select` 直接拒，而且连接是只读的，双保险 |
| "LLM 注入（提示词注入）呢？" | 用户输入里写"忽略以上指令"这类，我在 Understand 里判意图，命中注入样本就拒答；评测集里有 5 条注入题，拦截率 100%。但这是**样本级**防御，不是形式化保证 |
| "性能开销大吗？" | sqlglot 解析是毫秒级，相对 LLM 的几秒可以忽略 |

## 4. RAG：知识库怎么建、怎么证明有用

### 4.1 他会怎么问

- "你的 RAG 怎么做的？"
- "为什么用向量库，直接塞 prompt 不行吗？"
- "怎么证明检索是有效的？"

### 4.2 一句话答法

> 我把业务知识拆成四类——SQL 模板、表结构卡、业务词典、few-shot，一共 97 条；用 BGE-M3 转成 1024 维向量存 Milvus，检索走"向量 + BM25 混合 → RRF 融合 → rerank → MMR 去重 → 按类型配额"；然后用 81 道题做召回评测，R@5 从 0.778 提到 0.988。

### 4.3 展开

**为什么要分四类，而不是一个大知识库**：一个问题的上下文里，模板告诉模型"SQL 长什么样"，表卡告诉它"有哪些列"，词典告诉它"销售额和 GMV 是不是一回事"，few-shot 告诉它"这类问题标准答法是什么"。**四类各取 2~3 条**，拼出来的上下文既全又不超长；全塞进去会互相挤占，模型反而抓不住重点。

**检索链路**（`agent/app/rag/retriever.py:70`）：

```
query
  ├─ dense: BGE-M3 → Milvus top50
  └─ BM25 : jieba 分词 → 关键词 top50
        ↓
     RRF 融合（k=60，权重 [1.0, 0.6]，向量为主）
        ↓
     rerank（bge-reranker-v2-m3，top30 → top12）
        ↓
     MMR（λ=0.7，去掉近似重复）
        ↓
     按类型配额：3 模板 + 2 表卡 + 2 词典 + 1 few-shot
```

**版本化集合 + alias**：知识库不是"启动时 drop 重建"，而是每次灌库建一个新集合 `agent_knowledge_v{n}`，灌完把 alias `agent_knowledge` 指过去。**灌库不中断服务，出问题把 alias 指回上一版**。这是"玩具"和"能上线"的分界线。

**评测怎么做**（这是最能加分的地方）：

- 81 道题，每题标好应该召回哪个模板；
- 指标：Recall@1/3/5/10、MRR、nDCG@5；
- 消融：旧哈希向量 / 纯向量 / 纯 BM25 / 混合 / 混合+rerank / 再加 MMR+配额。

| 策略 | R@5 | MRR | nDCG@5 |
|---|---|---|---|
| 旧：md5 2-gram 哈希 256 维 | .778 | .742 | .738 |
| 纯向量 BGE-M3 | .963 | .924 | .932 |
| 纯 BM25 | .926 | .845 | .864 |
| 混合 RRF | .963 | .919 | .929 |
| **混合 + rerank** | **.988** | **.929** | **.944** |
| +MMR + 类型配额 | .938 | .914 | .915 |

**怎么读这张表**（面试官爱问"为什么加了东西反而降"）：

- 换真向量是最大的一步（.778 → .963），因为原来的"向量"是 md5 字符哈希，压根没有语义；
- 混合对整体几乎没提升——语料只有 97 条，向量已经接近饱和，BM25 只在**精确词**（品类名、字段名）上补位；但 hard 子集上 rerank 把 R@5 从 .765 拉到 .941，说明它救的是"排得不够前"，不是"召不回"；
- 最后一行降了，是因为 MMR 和配额**故意牺牲模板召回**，换上下文覆盖度——它们是给生成用的，不是给召回打分的。所以报告里检索能力看 `rerank` 那一行，生产链路用 `context` 那一行。

### 4.4 追问预判

| 追问 | 答法 |
|---|---|
| "为什么不直接把 50 个模板全塞 prompt？" | 97 条全塞约 3 万 token，贵且慢；更要命的是长上下文里模型抓不住重点。检索是为了"只给相关的 8 条" |
| "chunk 怎么切的？" | 模板本身就是一条完整知识（问题 + SQL + 口径），不用再切；表卡按表切。**没有为了切而切** |
| "embedding 为什么用 API 不用本地？" | 8G 卡跑本地 embedding 不是不行，但会和微调抢显存；API 成本很低，且模型可换。代价是离线不可用，所以做了磁盘缓存 |
| "Milvus 挂了怎么办？" | 降级到内存向量检索（同样接口），再不行降级为纯 BM25；`/health` 里能看到当前 `vector_store: milvus/inmemory` |
| "rerank 为什么只取 30 条？" | 全量 rerank 是 O(n) 次模型调用，97 条无所谓，但真实知识库上万条就必须截断；截断位置是延迟和效果的平衡点 |

## 5. 时间窗：为什么不让 LLM 算日期（真坑）

### 5.1 他会怎么问

- "用户说'上个月'，你怎么知道是哪个月？"
- "LLM 算日期不行吗？"

### 5.2 一句话答法

> 不行。LLM 没有"今天"的概念，它会用训练数据里的日期去推，或者干脆算错一个月。所以时间窗由规则引擎根据数据锚点算，算完以"已确定时间窗"的形式写进 prompt，并明确告诉模型"禁止自行推算日期"。

### 5.3 展开

```python
# agent/app/llm.py:42
def parse_date_window(question: str, anchor: str) -> dict:
    # 先匹配"最近 N 周"，再匹配"最近 N 天"，最后才是裸"最近"
    m = re.search(r"(?:最近|近|过去)\s*(\d+)\s*周", question)
    ...
    return {}      # 没有时间词 = 全量，不要默认加 30 天
```

这里踩过两个坑：

1. **"最近 8 周"被"最近"先匹配**，吞成了"最近 7 天"——正则顺序错了；
2. **函数末尾默认返回"最近 30 天"**，导致所有"整体销售额"的题都被悄悄加了时间过滤，评测全线偏低。

修完之后，`understand` 节点里还有一道保险：**LLM 给的 time_range 一律被规则引擎的结果覆盖**，LLM 只保留 intent / 维度 / 指标。

**为什么值得单独讲**：这是"确定性的事交给代码、模糊的事交给模型"的典型例子。面试官听到这里，会认为你想过职责边界，而不是"什么都丢给大模型"。

### 5.4 追问预判

| 追问 | 答法 |
|---|---|
| "数据锚点是什么？" | 库里的 `MAX(order_time)`，不是 `NOW()`。演示数据是历史数据，用 `NOW()` 会查出一堆空结果 |
| "锚点是 datetime 带时分秒怎么办？" | 必须 `DATE()` 取整再减天数，否则"最近 30 天"的第一天只剩 1 秒——这个 bug 让参考答案少统计了 2 万多元 |
| "用户说'双十一'呢？" | 目前只支持"最近 N 天/周/月、本月、上个月、今年"这些；节日要靠业务日历表，没做，属于已知缺口 |

## 6. 评测：怎么避免"自己骗自己"

### 6.1 他会怎么问

- "准确率 90% 怎么测的？"
- "怎么判断生成的 SQL 是对的？"

### 6.2 一句话答法

> 不比 SQL 字符串，比**执行结果集**。同一个问题可以有很多种写法，只要查出来的数一样就算对。79 道题分四类：可答、需要澄清、答不了、恶意注入，分别看执行准确率、澄清率、拒答率、拦截率。

### 6.3 展开

**判分规则**（`agent/app/eval/run_golden.py:87`）：

- 行数必须一致；
- 参考答案里的每个数值列，模型结果里都必须有，且四舍五入到 2 位后相等；
- 模型多出来的列（分子、分母、月份）忽略——它只是多给了信息，不算错；
- 多行结果按"共有列的多重集"比。

**为什么规则改了三版**：第一版要求"列完全一致"，模型多带一列分母就判错，误伤了 6 条；第二版改成"只比共有列"，又放过了"该有的指标没查"；第三版才是现在这样——**参考有的必须有，模型多的不追究**。

**数据集的构成**（79 条）：

| 类型 | 条数 | 看什么 |
|---|---|---|
| 可答 | 64 | 执行准确率 |
| 需要澄清 | 5 | 有没有反问，而不是瞎猜 |
| 答不了（预测未来、要建议） | 5 | 有没有拒答 |
| 恶意注入 | 5 | 有没有被带偏 |

**结果**（DeepSeek，temperature=0）：

| 配置 | valid SQL | 执行准确率 | 澄清率 | 拦截率 |
|---|---|---|---|---|
| 无 RAG | 57.8% | 12.5% | 100% | 80% |
| 有 RAG | 100% | **90.6%** | 100% | 100% |

**必须主动说的三句话**：

1. 同一份代码跑三次是 92.2 / 89.1 / 90.6，所以对外说"约 90%，±1.5 个点"，不说单次最高值；
2. 提升过程里有一轮是"对着模型输出改参考答案"，那轮的 92.2% **有水分**，后来把参考答案的 bug 修掉、重新跑，才敢用 90.6%；
3. 79 条里澄清/拒答/注入各只有 5 条，比例上的 100% 只能说明"没漏"，不能说明"稳"。

### 6.4 追问预判

| 追问 | 答法 |
|---|---|
| "参考答案错了怎么办？" | 踩过：模板里 `DATE_SUB` 没取整，锚点带时分秒，导致"最近 30 天"少算一天。用脚本逐条执行参考答案、和已知口径对数，才发现。**参考答案也要被测试** |
| "为什么不用 BLEU / 编辑距离比 SQL？" | 同一个结果有无数种 SQL 写法，字符串相似度和正确性不相关 |
| "90% 是不是过拟合评测集？" | 有可能。评测集和模板同源，模板题上表现好是必然的；所以又做了**留出模板**的微调评测（见第 7 节），那组数字低得多，才是真实泛化 |
| "怎么防止模型背答案？" | 题面做了同义改写（13 条 B 变体），但样本仍偏少，这是局限 |

## 7. 微调：1.5B 能学到什么，RAG 为什么帮倒忙

### 7.1 他会怎么问

- "为什么微调？prompt 不够吗？"
- "效果怎么样？"
- "为什么不上 7B？"

### 7.2 一句话答法

> prompt 解决不了"模型根本不知道你这套库长什么样"。我用 52 个模板合成 573 条训练数据，在 8G 卡上用 LoRA 微调 Qwen2.5-Coder-1.5B，只训 1.18% 的参数、17 分钟；在 11 个**从来没见过的模板**上，准确率从 0% 提到 35.1%。

### 7.3 展开

**数据怎么来**（`agent/finetune/synth.py`）：

```
52 个模板 → LLM 生成 8 种口语问法 → 换月份/品类实例化
        → 执行过滤（过白名单 + 结果非空）→ 按模板切分（5 留 1）
```

**为什么按模板切，不按样本随机切**：同一模板的不同问法 SQL 骨架几乎一样，随机切会让"见过的模板"泄漏到测试集，指标虚高。留出整个模板，才是真泛化。

**训练配置**（`agent/finetune/train_qlora.py:93`）：LoRA r=16、alpha=32、fp16、batch 1×8、lr 2e-4、3 epoch、max_len 1536，可训练参数 18.5M / 1.56B。

**四组对比**（77 题，全部来自留出模板）：

| 配置 | 准确率 |
|---|---|
| base | 0% |
| base + RAG | 0% |
| **LoRA** | **35.1%** |
| LoRA + RAG | 20.8% |

**三个必须讲出来的观察**：

1. base 不是"写得差"，是**编造不存在的表**（`JOIN products`）——它压根不知道这套库有什么，这就是微调要补的；
2. LoRA 从 0 到 35.1%，说明"领域 schema + 模板写法"是能灌进去的；剩下 65% 主要是没见过的模板结构和多表 JOIN；
3. **RAG 对微调后的小模型是负收益**（35.1% → 20.8%）：训练时输入里没有检索上下文，推理时突然多 1200 字符，分布不一致；1.5B 的上下文容量有限，长检索把 schema 挤出了注意力。**而在 DeepSeek 上 RAG 是 12.5% → 90.6%**。所以结论不是"RAG 有用/没用"，而是"RAG 的收益取决于模型能不能消化上下文"。

### 7.4 追问预判

| 追问 | 答法 |
|---|---|
| "为什么不上 7B？" | 8G 显存，7B 就算 4bit 也很紧，Windows 上 bitsandbytes 还不稳；1.5B 能在同一台机器上反复跑四组对比，**对比比参数量更有价值** |
| "为什么不用 QLoRA？" | 同上，4bit 在 Windows 环境踩坑成本高；1.5B fp16 只占 3G，没必要量化 |
| "35% 也太低了，能用吗？" | 不能用，它本来就不是线上方案。定位是"成本敏感场景的降级候选"和"证明领域适配有效"，线上仍然是 DeepSeek |
| "reranker 微调了吗？" | 脚本写了（`finetune/train_reranker.py`），但**没训**：只有 81 对样本，训完在同一个 81 题上评必然过拟合，数字不可信。这是取舍，不是漏做 |

## 8. 流式、降级与工程化

### 8.1 他会怎么问

- "为什么用 SSE 不用 WebSocket？"
- "依赖的服务挂了怎么办？"
- "多轮对话怎么做的？"

### 8.2 一句话答法

> 问数是"一问一答 + 中间过程推送"，SSE 单向就够了，还能走普通 HTTP、断线自动重连；每条链路都有降级：Milvus 挂了走内存检索，Redis 挂了走进程内，PG 挂了直接关掉长期记忆，主链路不崩。

### 8.3 展开

**SSE 的两个细节**：

- 事件类型分开：`thinking` / `sql` / `answer` / `chart` / `done`，前端按类型渲染，不用等整段结束；
- **15 秒没事件就发心跳**（`app/orchestrator.py`），否则中间的反向代理会认为连接空闲超时断开——长任务（LLM 生成 10 秒）最容易踩。

**降级不是"try/except 吞掉"**：

| 依赖 | 挂了之后 | 用户看到 |
|---|---|---|
| Milvus | 内存向量检索 → 再不行纯 BM25 | 结果稍差，不报错 |
| Redis | 进程内会话 | 多实例下会话不共享，单机无感 |
| PostgreSQL | 关闭长期记忆 | 功能缺失，主链路正常 |
| LLM | 规则兜底理解 + Mock 分析 | 能出 SQL 和固定结论，不白屏 |

`/health` 里每一项都带状态和耗时：PG 探测 2 秒超时后返回 `degraded`，不会把整个健康检查拖死——**健康检查自己不能成为故障点**。

### 8.4 追问预判

| 追问 | 答法 |
|---|---|
| "多轮上下文怎么存？" | Redis 存最近 N 轮，超长做摘要；PG 做长期归档。PG 没起的时候只有 Redis，重启即丢 |
| "并发高了会怎样？" | 没压测过。已知瓶颈是 LLM 的 TPS 和单进程的 async 队列；要做的话是加实例 + 网关限流 |
| "为什么不用 LangChain 的 AgentExecutor？" | 它的循环是"模型自己决定调哪个工具"，不可控；问数需要固定的阶段和可插拔的自检，StateGraph 更合适 |

## 10. 三个真坑（讲故事素材）

### 坑 1：改了 11 处日期，才让"最近 30 天"真的等于 30 天

> 评测一直有个诡异现象："最近 30 天销售额"总比手工算的少 2 万多。
> 查到最后是模板里 `DATE_SUB((SELECT MAX(order_time) FROM orders), INTERVAL 30 DAY)`：锚点是 `2026-12-31 23:59:59`，减 30 天得到 `2026-12-01 23:59:59`，于是 12-01 这一天只统计了最后 1 秒。
> 11 个模板都有这个问题。修法是先 `DATE()` 取整再减。
> **教训**：时间在系统里有三个精度（Java 纳秒、MySQL 秒、业务天），任何一处没对齐，"最近 N 天"就不是你以为的那 N 天。

### 坑 2：判分规则比模型更容易错

> 第一次跑评测，18 条"失败"里有一半是判分误伤：模型多查了一列分母、单行结果少带了一个月份列，数其实是对的。
> 我一开始想"改判分规则把分提上去"，后来发现这跟改参考答案没有区别——**指标一旦可以调，就不再是指标**。
> 最后是逐条看：12 条真错，6 条判分错。改判分规则时把每一次修改的理由写进文档，防止自己下次又"顺手放宽"。
> **教训**：评测系统的 bug 比被测系统的 bug 更危险，因为它会把错的方向反馈给你。

### 坑 3：写中文代码文件，别用 shell 重定向

> 用 PowerShell 往 Python 文件里追加中文注释，文件被按 GBK 写进去，Python 直接 `SyntaxError: 'utf-8' codec can't decode`。
> 更麻烦的是文件已经半损坏，只能按字节截断到最后一个完整函数，再整文件重写。
> **教训**：编码问题不要靠"再试一次"解决，要固定工具（编辑器统一 UTF-8）和固定入口（不要用 `>`、`Set-Content` 写源码）。
