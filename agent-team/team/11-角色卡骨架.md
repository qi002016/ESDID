# 11 · 角色卡骨架（新增角色用）

> 当项目需要 PM / ARCH / FE / BE / QA / OPS 之外的角色（如数据工程师、算法工程师、安全工程师、文档工程师）时，**照本骨架新建一张角色卡**，不要临时在对话里口头定义职责。

## 使用步骤

1. 复制本文件为 `<下一序号>-<角色名>.md`（序号顺延，**当前已用至 `12-UI设计师.md`，下一张从 `13-` 开始**）。
2. 填满 ①–⑧ 八段。**② 边界和 ⑧ DoD 最容易漏，但最重要**。
3. 在 `00-团队总纲.md` 第一节的团队构成表里加一行。
4. 在 `09-升级矩阵与决策权.md` 第一节决策权表里补上该角色的拍板范围。
5. 若该角色有专属工件，在 `10-工件规范.md` 第二节命名表与第五节字段表里加一行；有新的工件目录时，在第一节目录结构里也加一行。
6. 把新角色卡文件名加进 `SKILL.md` 的装载顺序表，以及 `install.ps1` 的 `$ROLE_FILES`（否则单文件版与安装包会漏掉它）。

> **照着 `12-UI设计师.md` 抄**：那是一张按本骨架完整落地的样板，五个登记点全都同步过了。

## 骨架模板

```markdown
# NN · <角色中文名> Agent（<缩写>）

> 启动时先读：`00-团队总纲.md`、`09-升级矩阵与决策权.md`、`10-工件规范.md`，再读本卡。

## ① 职责
<用一句话说清「这个角色把什么变成什么」。必须是可交付的动作，不是「负责 X 相关事宜」。>

## ② 边界（不做）
<列出 4–6 条具体的不做事项，以及「不做时应该把事交给谁」。
这一节是防止多 Agent 互相踩踏的核心，务必具体。>

## ③ 输入
<列路径。写清「只读哪几份」，避免全仓库扫读。>

## ④ 输出工件
| 工件 | 路径 | 最小字段 |
| --- | --- | --- |
| … | `docs/team/<子目录>/<TYPE>-nnn-<slug>.md` | … |

**长度上限**：<多少页，超了怎么办>

## ⑤ 工作流 SOP
1. 确认前置：<开工的必要条件，如契约已 FROZEN / 上游工件已 ACCEPTED>
2. …
3. 自测/自查并**记录真实证据**
4. 写工件
5. 提交验收；被打回按打回单修订

## ⑥ 升级条件
| 情况 | 动作 |
| --- | --- |
| 收到越界任务 | 报主 Agent 重新分派 |
| 上游工件不合格 | 打回上游（抄送主 Agent） |
| 需要改需求/契约 | 走 CR / CC 流程 |
| 出现争议 | 报主 Agent 裁决 |

## ⑦ 自检清单
- [ ] <只写「能验证真假」的条目，不要写「要认真负责」这类废话>
- [ ] ≤ 12 条

## ⑧ 完成定义（DoD）
<用 4–6 条可验证条件描述「什么时候算做完」，并指明对应哪个门禁。>

## ⑨ 记忆规则
写入 `docs/team/memory/<角色>.md`：<该角色最该长期记住的东西>。
```

## 填写质量要求

| 段落 | 合格标准 | 常见错误 |
| --- | --- | --- |
| ① 职责 | 一句话说清输入→输出 | 「负责相关事宜」这种无法验收的表述 |
| ② 边界 | 具体到「不做 X，交给 Y」 | 只写「不越界」等于没写 |
| ③ 输入 | 给路径，且限定范围 | 让它「了解整个项目」 |
| ④ 输出 | 路径 + 最小字段 + 长度上限 | 只说「提交报告」 |
| ⑤ SOP | 有前置条件检查、有证据要求 | 直接从「开始工作」写起 |
| ⑥ 升级 | 覆盖越界/上游不合格/争议 | 漏掉「上游不合格怎么办」 |
| ⑦ 自检 | 每条能判真假 | 「注意代码质量」 |
| ⑧ DoD | 可验证，绑定门禁 | 「功能完成」 |

## 什么时候**不该**新增角色

- 只是工作量大的同一类活 → 属于现有角色，不要拆角色。
- 只是「需要更仔细」→ 属于自检清单，不要拆角色。
- 职责无法用「输入→输出工件」描述 → 说明它不是角色，而是一个**流程步骤**。

**角色越多，协调成本越高。** 小项目允许一人兼多角，但同一交付物不得由实现者自己验收。
