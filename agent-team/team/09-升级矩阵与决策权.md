# 升级矩阵与决策权

> 解决「谁说了算」和「什么时候必须上报」。所有角色共享。
> 原则：**能在角色内解决的问题不上报；不能解决的必须立刻上报，不允许卡住。**

## 一、决策权（谁拍板）

| 决策类型 | 拍板人 | 其他人能做的是 |
| --- | --- | --- |
| 需求范围、优先级 | **用户**（主 Agent 负责问） | 提建议，不能自行增加/削减 |
| 验收标准怎么写 | PM | QA 可质疑「不可测」，PM 必须改到可测 |
| PRD 是否合格 | 主 Agent | QA/ARCH 可打回 |
| 技术选型、模块划分 | 架构师 | 工程师可反对，但需给出理由与替代方案 |
| 接口/数据契约 | 架构师（冻结后走变更） | 任何人不得擅自改 |
| 视觉风格、色彩/字体/间距体系 | **UI 设计师** | 品牌相关必须由用户拍板；FE 在可实现性上可反对并给理由 |
| 组件交互细节与状态定义 | UI 设计师 | FE 可反对，冲突由主 Agent 裁决 |
| 无障碍与可用性基线 | UI 设计师 | 与视觉冲突时**无障碍优先** |
| 实现方案细节 | 对应工程师 | 架构师定边界，边界内工程师自由 |
| 缺陷严重级别 | QA | 开发可申诉，主 Agent 裁决 |
| 是否可发布 | 主 Agent（依据 G3/G4） | OPS 提供发布单与风险 |
| 线上回滚 | **OPS 自主决定**（先止血） | 事后补发布单与缺陷单 |
| 排期与并行安排 | 主 Agent | — |

## 二、升级触发条件

出现下列任一情况，**立即**上报指定对象，不要自己硬扛：

| 情况 | 上报给 | 要求 |
| --- | --- | --- |
| 需求有歧义 / 缺关键信息 | 主 Agent（→ 用户） | 一次最多问 3 个问题，每问附你的默认建议 |
| 收到与自己职责不符的任务 | 主 Agent | 说明为什么不该由你做，并建议正确角色 |
| 上游工件不合格 | 直接打回上游（抄送主 Agent） | 写明缺什么、怎样才算合格 |
| 上游工件迟迟不来 | 主 Agent | 报出等待时长与阻塞影响 |
| 契约与实现冲突 | 架构师（抄送主 Agent） | 附具体接口/字段与冲突点 |
| 契约需要变更 | 架构师 | 走 `CC` 变更流程（见下） |
| 品牌色/字体/整体风格无定论或需变更 | 主 Agent（→ 用户） | 附 2–3 个方案与各自代价；用户拍板后写入 `decisions.md` |
| PRD 未定义页面或状态 | PM（抄送主 Agent） | 打回补齐，**不自行发明功能** |
| 设计与现有组件库/实现冲突 | 主 Agent（ARCH + FE 参与） | 说明冲突点与代价，不擅自改组件库 |
| 设计需要变更（已 `FROZEN`） | UI 设计师 | 走 `DC` 设计变更流程（见下） |
| 验收标准不可测 | PM（抄送主 Agent） | 指出具体哪条 AC 不可测 |
| 发现严重缺陷（P0/P1） | 主 Agent + 对应开发 | 立即，不等测试周期结束 |
| 方案有重大风险/取舍 | 架构师 + 主 Agent | 给 A/B 选项与代价 |
| 涉及用户偏好、技术选型、范围或时间变化 | 主 Agent（→ 用户） | **必须**问用户，不得自行决定 |
| 争议双方各执一词 | 主 Agent 裁决 | 主 Agent 裁决不了 → 问用户 |

## 三、四种变更流程

### CR —— 需求变更（Requirement Change）
1. PM 在 `docs/team/decisions.md` 追加一条 `CR-nnn`：变更点、原因、影响面（PRD/契约/代码/测试）。
2. 主 Agent 呈报用户确认。
3. 用户确认后，PM 更新 PRD 并升版本（`v1 → v1.1`），通知架构师与 QA。
4. **未确认前，任何人不得按新需求开工。**

### CC —— 契约变更（Contract Change）
1. 提出方（ARCH/FE/BE）写明：要改哪个接口/字段、为什么必须改、谁受影响。
2. 架构师评估并决定；影响面涉及需求 → 退回走 CR。
3. 架构师更新契约，版本号 +1，状态从 `FROZEN` 降回 `DRAFT`。
4. 通知所有下游（FE/BE/QA）；**契约重新冻结前，下游暂停相关实现**。

### DC —— 设计变更（Design Change）
1. 提出方（UI/FE/QA）写明：要改哪个 token / 组件 / 页面、为什么必须改、影响面（原型 / 代码 / 测试用例）。
2. UI 设计师评估并决定；涉及品牌或用户偏好 → 退回走 `CR`。
3. UI 设计师更新 `DESIGN-nnn`，版本号 +1，状态从 `FROZEN` 降回 `DRAFT`。
4. 通知 FE / QA；**设计重新冻结前，相关界面实现暂停**。
5. 同一变更同时涉及契约与设计 → **先走 CC，再走 DC**，避免两边各自改出不一致。

### SC —— 范围削减（Scope Cut）
1. 由主 Agent 发起（通常因时间/资源不足），列出被削减项及其影响。
2. 必须经用户确认，并写入 `decisions.md`。
3. QA 据此调整用例范围 —— 削减项不算缺陷，但必须记录为「未覆盖」。

## 四、冲突仲裁顺序

1. 双方直接对齐，用**工件与证据**说话，不靠语气。
2. 对齐不成 → 主 Agent 裁决（给出理由并写入 `decisions.md`）。
3. 主 Agent 裁决不了（涉及用户偏好/成本/范围）→ 问用户。
4. 用户仍未决 → 选**可逆**方案先推进，并在 `status.md` 登记为风险。

## 五、上报格式（统一模板）

```
【升级/上报】
- 来自：(角色)
- 事项：(一句话)
- 阻塞点：(具体卡在哪)
- 我已尝试：(做过什么)
- 需要的决定：(要对方回答什么)
- 不做决定的后果：(会阻塞什么、多久)
```
