# 通用研发团队（agent-team）

一套**所有项目都能用**的多角色 Agent 团队框架。把「模糊需求」变成「可交付、可验收的成果」，角色之间靠**标准工件**交接，而不是靠对话。

```
用户需求
  └─ 主 Agent（统筹/验收/交付）
       ├─ 产品经理 → PRD（含可验证的验收标准）
       ├─ 架构师   → 接口与数据契约（FROZEN 后下游才开工）
       ├─ UI 设计师 → 界面规范 + 静态原型（与架构并行，同样 FROZEN 后前端才开工）
       ├─ 前端/后端 → 代码 + MR
       ├─ 测试     → 测试报告 + 缺陷单（只验证不修复）
       └─ 运维     → 发布单（含回滚方案）
```

## 5 分钟上手

### 方式一：全局安装（推荐，一次装好，所有项目可用）

```powershell
cd D:\ESDID\agent-team
powershell -NoProfile -ExecutionPolicy Bypass -File .\install.ps1 -Global
```

> 加 `-ExecutionPolicy Bypass` 是为了避开脚本执行策略拦截；装了 PowerShell 7 的话把 `powershell` 换成 `pwsh` 也可以。
> 通过 DSH 工具调用时同样需要它，因为受限会话下未签名脚本会被拒绝加载。

安装后：
- 团队包 → `~/.agents/skills/agent-team/`
- 精简版总纲 → `$DSH_HOME/AGENTS.md`（标记块注入，**所有项目的所有会话**都生效）
- 原 `AGENTS.md` 自动备份，只替换标记块，**绝不整体覆盖**

> **需要新开一个会话**，skill 才会出现在技能目录里。

### 方式二：单个项目安装

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\install.ps1 -Project D:\path\to\your-project
```

安装后在该项目里生成：
- `.agents/skills/agent-team/`（团队包）
- `docs/team/`（工件目录 + `config.md`/`plan.md`/`status.md`/`decisions.md` 骨架）

### 卸载

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\install.ps1 -Uninstall
```

只删全局 skill 与 `AGENTS.md` 标记块，保留其他内容与备份。

## 怎么用

新项目开工时：

1. 填 `docs/team/config.md` —— **可写范围、构建/测试/启动命令、端口、红线**。这是团队的唯一环境事实来源。
2. 主 Agent 走 `team/01-主Agent.md` 的 G0–G5 门禁流程：
   - **G0** 需求澄清（AC 必须可验证）
   - **G1** 冻结（契约 FROZEN；有界面变更时设计规范也须 FROZEN）
   - **G2** 实现完成 + 自测证据
   - **G3** 测试通过（P0/P1 = 0）
   - **G4** 发布单含回滚方案
   - **G5** 交付归档
3. 每个角色只加载 `00 → 09 → 10 → 自己的角色卡`，不要全量读。
4. 需求完成后更新 `status.md`，复盘写 `reviews/RETRO-nnn.md`，改进项回写角色卡。

## 每张角色卡的结构（九段）

① 职责 → ② 边界（不做）→ ③ 输入 → ④ 输出工件 → ⑤ 工作流 SOP → ⑥ 升级条件 → ⑦ 自检清单 → ⑧ 完成定义（DoD）→ ⑨ 记忆规则

**②边界和⑧DoD 是整套框架真正的价值所在**：多 Agent 失败通常不是因为能力不够，而是因为职责重叠、验收标准含糊、交付物不统一。

## 设计取舍（为什么这样做）

| 做法 | 理由 |
| --- | --- |
| 交接靠文件而非对话 | 对话不留痕，换会话就丢；文件可被下一个 Agent 读到 |
| 契约 `FROZEN` 后才允许前端/后端开工 | 并行开发的最大返工源是接口对不上 |
| UI 设计与架构设计**并行** | 两者都只依赖 PRD，串行只是白白拉长前置期；两个工件都冻结后前端才动工 |
| 静态原型放 `docs/team/design/`，不进前端源码目录 | 避免 UI 与 FE 的可写范围重叠、互相覆盖 |
| 测试只验证不修复 | 实现者自测自验会系统性放宽标准 |
| 每个工件设**长度上限** | 文档越长越没人读，规范反而失效 |
| AC 禁止出现「友好/快速/合理」 | 无法判真假的验收标准等于没有标准 |
| 全局只注入精简总纲 | 全量角色卡会白吃每个会话的上下文 |
| 自检清单 ≤ 12 条、铁律 ≤ 15 条 | 规则太多等于没有规则 |
| 记忆条目强制三段式 | 便于 grep，避免记忆本身爆上下文 |
| 复盘必须回写角色卡 | 不回写的复盘，团队停在第一天 |

## 小项目怎么办

**允许一人兼多角**，但必须守住一条：**同一交付物不得由实现者自己验收**。小事（单文件改动、查资料、一次性脚本）**直接做，不要起团队** —— 流程成本必须小于返工成本。

## 扩展新角色

复制 `team/11-角色卡骨架.md`，按骨架填满八段，然后走完骨架列出的 **5 个登记点**：`00-团队总纲.md`（构成表 + 门禁表）、`09-升级矩阵与决策权.md`（决策权表 + 升级触发表）、`10-工件规范.md`（目录/命名/字段表）、`SKILL.md`（装载顺序）、`install.ps1`（`$ROLE_FILES`，否则单文件版会漏掉它）。

**照着 `12-UI设计师.md` 抄** —— 那是按骨架完整落地的样板，五个登记点全部同步过。**角色越多协调成本越高**，能不加就不加。

## 常见问题

**Q：装了但技能目录里没有 `agent-team`？**
新 skill 需要**新开会话**才会被扫描到。已运行的会话不会自动感知。

**Q：会覆盖我已有的 `AGENTS.md` 吗？**
不会。安装器只在 `<!-- agent-team:begin -->` 与 `<!-- agent-team:end -->` 之间写入，其余内容原样保留，并先做带时间戳的备份。重复安装是幂等的。

**Q：全局注入会不会很吃上下文？**
精简版约 30 行。若加 `-FullOutline` 会把全部角色卡注入每个会话，**显著增加开销**，只在确实需要时用。

**Q：改了角色卡要重装吗？**
不用重装，但需要让 skill 重新加载（新会话）。改 `$DSH_HOME/AGENTS.md` 则**下一个请求**即生效。

**Q：能用在 Claude Code / Cursor 上吗？**
能。见 `team/adapters/DSH.md` 第八节：`~/.agents/skills` 是跨工具共享约定；总纲写入对应工具的全局指令文件（Claude Code 用 `~/.claude/CLAUDE.md`，Cursor 用 `.cursorrules`）。
